# Заявки: общий интерфейс фронтенда и бэкенда

Статус: контракт для параллельной разработки, версия 1. В исходной версии endpoint отсутствует. Этот документ фиксирует будущий интерфейс, а не подтверждает его реализацию. Менять его односторонне нельзя; изменение согласуется через PR.

## Разделение файлов

Фронтенд меняет визуал и HTML, сохраняя перечисленные ниже hooks. Бэкенд владеет `site/scripts/forms.js`, преобразованием полей в запрос и состояниями отправки. Визуальное оформление новых состояний согласуется с фронтендом. API размещается на подтверждённой серверной платформе; секретов и сетевого вызова Telegram в браузере быть не должно.

Текущие hooks: `#project-form`, `#project-dialog`, `.dialog-form-slot`, `.dialog-close`, `.form-status`, `.comment-label`, `.product-field`, `.interest-grid`, `.interest-option`, `.selected-model`, CTA с `data-product` и `data-model`. Имена полей: `name`, `phone`, `product`, `interests`, `comment`, `consent`. Не менять эти значения при перестройке визуала без согласования.

Секция→направление: `drinkx`→DrinkX, `wendougee`→Wendougee, `linkbar`→LinkBar, `coffee`→Кофе и СТМ, `xlvi-ceado`→XLVI / Ceado, `water`→Водоподготовка, `horeca`→Комплектация. Общая форма — отдельный контекст. Карточки моделей сейчас не кликабельны; `model` не подставляется по одному наведению.

## Будущий запрос

`POST /api/leads`, `Content-Type: application/json`, по умолчанию на том же origin. Любой отдельный API-origin и CORS согласовываются до подключения.

```json
{
  "schemaVersion": 1,
  "name": "Анна",
  "phone": "+79000000000",
  "product": "drinkx",
  "interests": [],
  "model": null,
  "comment": "Станция для офиса",
  "consent": true,
  "source": "brand-modal"
}
```

- `name`: строка после trim, 2–100 символов.
- `phone`: нормализованный российский номер `+7` и десять цифр. Пользователь видит прежнюю маску `+7 (___) ___-__-__`.
- `product`: `drinkx`, `wendougee`, `linkbar`, `coffee`, `xlvi-ceado`, `water`, `horeca` или `null` для общей заявки.
- `interests`: в общей заявке непустой массив этих же идентификаторов или единственный `undecided` («Помогите определиться»); при заданном `product` пустой массив. Подписи чекбоксов остаются русскими, преобразование выполняется в `forms.js`.
- `model`: явно выбранная модель, до 120 символов, либо `null`. Отсутствие выбора не заполнять выдуманным значением.
- `comment`: необязательная строка, до 1000 символов; пустая строка допустима.
- `consent`: строго `true`.
- `source`: `hero-modal`, `brand-modal` или `inline`.

Сервер независимо валидирует тело, допустимые направления, размеры и обязательные значения. Не доверять данным браузера и не включать в сообщения технический HTML пользователя без экранирования.

## Ответы и состояния

Успех: `200` и JSON `{"ok":true,"requestId":"server-generated-id"}`. Возвращать его только после подтверждённого успешного ответа Telegram. Если позже потребуется очередь, её семантика и хранение согласуются отдельно.

Ошибка: JSON вида `{"ok":false,"code":"VALIDATION_ERROR","fieldErrors":{"phone":"Введите номер полностью"}}`. Использовать `400` для неверных полей, `413` для слишком большого тела, `429` для ограничения частоты, `502/503` для проблем доставки/конфигурации. Не раскрывать токен, chat ID, полный upstream-ответ или содержимое чужих заявок.

Состояния формы: готова → отправляется → подтверждённый успех / понятная ошибка. Пока запрос выполняется, повторная отправка блокируется. При ошибке заполнение и контекст сохраняются; ложный успех и автоматические повторы с риском дублей недопустимы. Продумать защиту от повторных запросов и честное поведение при неопределённом результате доставки.

Нативный dialog, независимые черновики брендов, синхронизация двух общих форм, +7, звёздочки, множественный выбор и возврат фокуса сохраняются. В исходной версии отправка намеренно отсутствует; подключение делает бэкенд-разработчик.

## Конфигурация и приёмка

Бэкенд получает `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` из серверного окружения; в Git — только пустые примеры. Получателя, платформу размещения и тестовый чат уточняет у Романа, не угадывает по публичному Telegram-профилю Дмитрия. Проверка с реальным получателем отдельно согласуется.

До production необходимо определить документы и текст согласия для приёма персональных данных. Не сочинять юридические реквизиты и готовую политику. Без подтверждённых данных можно завершать код, локальные тесты и проверку с mock Telegram, явно отмечая оставшиеся настройки.

Проверки: общая/брендовая/нижняя заявки, несколько направлений, пустые/невалидные поля, сохранение контекста, отклонённое согласие, двойное нажатие, timeout, отказ Telegram и отсутствие секретов в публичных файлах/логах. Хранилище заявок, CRM, оплата и другие внешние интеграции этим контрактом не добавлены.
