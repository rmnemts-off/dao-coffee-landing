# Заявки: общий интерфейс фронтенда и бэкенда

Статус: контракт версии 1. По прямому решению владельца от 25.10.2026 доставка выполняется только в Bitrix24; Telegram исключён. JSON-запрос и ответы сохраняются. Адаптер проверяется с mock до подключения конкретного портала. Другие изменения контракта согласуются через PR.

## Разделение файлов

Фронтенд меняет визуал и HTML, сохраняя перечисленные ниже hooks. Бэкенд владеет `site/scripts/forms.js`, преобразованием полей в запрос и состояниями отправки. Визуальное оформление новых состояний согласуется с фронтендом. API размещается на подтверждённой серверной платформе; секретов и сетевого вызова Bitrix24 в браузере быть не должно.

Текущие hooks: `#project-form`, `#project-dialog`, `.dialog-form-slot`, `.dialog-close`, `.form-status`, `.comment-label`, `.product-field`, `.interest-grid`, `.interest-option`, `.selected-model`, CTA с `data-product` и `data-model`. Имена полей: `name`, `phone`, `product`, `interests`, `comment`, `consent`. Не менять эти значения при перестройке визуала без согласования.

Секция→направление: `drinkx`→DrinkX, `wendougee`→Wendougee, `linkbar`→LinkBar, `coffee`→Кофе и СТМ, `xlvi-ceado`→XLVI / Ceado, `water`→Водоподготовка, `horeca`→Комплектация. Общая форма — отдельный контекст. Карточки моделей сейчас не кликабельны; `model` не подставляется по одному наведению.

## Запрос

`POST /api/leads`, `Content-Type: application/json`, `Idempotency-Key: <UUID v4>`, по умолчанию на том же origin. Любой отдельный API-origin и CORS согласовываются до подключения.

```json
{
  "schemaVersion": 1,
  "name": "Анна",
  "phone": "+79000000000",
  "product": "drinkx",
  "interests": [],
  "model": null,
  "comment": "Станция для офиса",
  "consent": true,
  "source": "brand-modal"
}
```

- `name`: строка после trim, 2–100 символов.
- `phone`: нормализованный российский номер `+7` и десять цифр. Пользователь видит прежнюю маску `+7 (___) ___-__-__`.
- `product`: `drinkx`, `wendougee`, `linkbar`, `coffee`, `xlvi-ceado`, `water`, `horeca` или `null` для общей заявки.
- `interests`: в общей заявке непустой массив этих же идентификаторов или единственный `undecided` («Помогите определиться»); при заданном `product` пустой массив. Подписи чекбоксов остаются русскими, преобразование выполняется в `forms.js`.
- `model`: явно выбранная модель, до 120 символов, либо `null`. Отсутствие выбора не заполнять выдуманным значением.
- `comment`: необязательная строка, до 1000 символов; пустая строка допустима.
- `consent`: строго `true`.
- `source`: `hero-modal`, `brand-modal` или `inline`.

Сервер независимо валидирует тело, допустимые направления, размеры и обязательные значения. Не доверять данным браузера и не включать в сообщения технический HTML пользователя без экранирования.

## Ответы и состояния

Успех: `200` и JSON `{"ok":true,"requestId":"server-generated-id"}`. Возвращать его только после подтверждённого создания лида или сделки в Bitrix24 (создание одного контакта ещё не успех). Перед REST-вызовом заявка сохраняется в постоянном журнале PostgreSQL. Сохранение в БД само по себе не означает успех доставки. Фоновая автоматическая отправка не включена.

Ошибка: JSON вида `{"ok":false,"code":"VALIDATION_ERROR","fieldErrors":{"phone":"Введите номер полностью"}}`. Использовать `400` для неверных полей, `413` для слишком большого тела, `429` для ограничения частоты, `502/503` для проблем доставки/конфигурации. Не раскрывать URL вебхука, внутренние ID CRM, полный upstream-ответ или содержимое чужих заявок.

Состояния формы: готова → отправляется → подтверждённый успех / понятная ошибка. Пока запрос выполняется, повторная отправка блокируется. При ошибке заполнение и контекст сохраняются; ложный успех и автоматические повторы с риском дублей недопустимы. Продумать защиту от повторных запросов и честное поведение при неопределённом результате доставки.

Нативный dialog, независимые черновики брендов, синхронизация двух общих форм, +7, звёздочки, множественный выбор и возврат фокуса сохраняются. В исходной версии отправка намеренно отсутствует; подключение делает бэкенд-разработчик.

## Конфигурация и приёмка

Бэкенд получает `BITRIX_WEBHOOK_URL` и согласованные ID типа карточки, ответственного, воронки/стадии из серверного окружения; в Git — пустые примеры. До записи проверяются режим CRM, поля и REST-права. Сначала выполняются только чтение настроек и mock-тесты; реальная тестовая карточка и возможный запуск роботов согласуются отдельно. Telegram больше не является получателем или запасным каналом.

До production необходимо определить документы и текст согласия для приёма персональных данных. Не сочинять юридические реквизиты и готовую политику. Без подтверждённых данных можно завершать код, локальные тесты и проверку с mock Bitrix24, явно отмечая оставшиеся настройки.

Проверки: общая/брендовая/нижняя заявки, несколько направлений, пустые/невалидные поля, сохранение контекста, отклонённое согласие, двойное нажатие, timeout, отказ Bitrix24 и отсутствие секретов в публичных файлах/логах. Подключается только Bitrix24. По поручению владельца добавлен постоянный журнал SQLite и восстановление после неопределённых ответов; схема — [CRM_DATA_FLOW.md](CRM_DATA_FLOW.md). Оплата и другие внешние интеграции не добавлены.

## Повторы и постоянное хранение (расширение от 25.10.2026)

Тело версии 1 сохраняется. Новый фронтенд передаёт обязательный `Idempotency-Key` UUID v4. При timeout/ошибке и повторной ручной отправке неизменённых данных ключ остаётся прежним; после подтвержденного успеха или изменения данных выдаётся новый. Общая modal/inline разделяют одну идентичность без поля `source`. В sessionStorage сохраняются только SHA-256 хеши и UUID; сами черновики остаются в памяти. При недоступном хранилище ключ живёт до закрытия страницы. Закрытие вкладки/очистка storage могут удалить ключ: межустройственная дедупликация не обещается.

Один ключ с другим нормализованным телом → `409 IDEMPOTENCY_CONFLICT`; отсутствующий/невалидный ключ → `400 INVALID_IDEMPOTENCY_KEY`. При занятой обработке → `503 DELIVERY_PENDING`. При неопределённой записи повтор проверяет CRM по `originId`, не создаёт вторую карточку. Ноль найденных карточек не доказывает неуспех прежней записи. При неоднозначности заявка остаётся в журнале для ручного разбора. Автоматических повторов нет.

## Представление обращения менеджеру (уточнение без изменения JSON v1)

Названия новых сделок: `Сайт DAO — <направления>` и модель, только если она явно выбрана. Общая форма с множественным выбором перечисляет все направления; `undecided` отображается как «Нужен совет». `sourceId` остаётся общим каналом «Веб-сайт», а конкретный блок выводится из проверенного `source`/`product`: `hero`, `contact` либо ID направления. Блок и форма сохраняются в стандартном поле `sourceDescription` и комментарии; вопрос клиента — полным текстом в начале комментария. Отдельный тип «прайс / технический вопрос» не вводится.

Постоянное production-хранилище — PostgreSQL с отдельными клиентами, обращениями,
связями направлений и журналом доставки: [POSTGRES_ARCHITECTURE.md](POSTGRES_ARCHITECTURE.md).
Внешние поля и ответы v1 сохранены; SQLite используется только для mock и переноса старых данных.
