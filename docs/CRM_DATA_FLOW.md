# Заявки DAO: данные сайта, журнал и Bitrix24

Реализация объединяет UX/UI `frontend/design` (исходный head `ae52340`) с серверной веткой `backend/telegram` (исходный head `0f9851d`). Внешний endpoint — `POST /api/leads`; «лид» в имени endpoint означает входящую заявку. На проверенном портале включена простая CRM, поэтому создаются контакт и сделка.

## Статус повторной проверки

Локальная ветка обновлена из `origin/backend/telegram` до `9402884`. Read-only проверка VPS подтвердила опубликованный релиз `8d7e28c`, активный API и отсутствие `backend/store.mjs`. Следовательно, постоянный журнал этой локальной ветки ещё не опубликован. Точная проверка CRM подтвердила одну тестовую сделку: общая воронка, стадия «Новая заявка», источник «Веб-сайт». Её тестовый payload был общей заявкой с `undecided`, поэтому оборудование в ней отсутствует по исходным данным.

По текущему поручению подготовлена архитектура **одной PostgreSQL БД** с клиентами, заявками, направлениями и историей доставки: [POSTGRES_ARCHITECTURE.md](POSTGRES_ARCHITECTURE.md), DDL — `backend/db/postgres-schema.sql`. Это проект следующего хранилища, пока не подключённый к runtime. SQLite ниже описывает действующий локальный код, а не окончательный выбор архитектуры и не состояние production.

## От формы до менеджера

1. Брендовая CTA задаёт `product`; модель берётся только из явно указанного `data-model`. Карточки/hover сами не выбирают модель.
2. Общая форма сохраняет несколько `interests` либо `undecided`; брендовая — одно направление, без массива интересов. Цель обращения «прайс/технические данные» не вводится.
3. Сервер проверяет имя, российский телефон, согласие, список направлений и размер текста. Сохраняет нормализованный снимок в SQLite до обращения к CRM.
4. По телефону ищет контакт. Один найденный используется без перезаписи; ноль — новый контакт. Несколько совпадений требуют ручного разбора.
5. Создаёт новую сделку с отдельным номером заявки даже при существующей активной сделке клиента. Название содержит все выбранные направления и явно выбранную модель: «Сайт DAO — DrinkX», «Сайт DAO — DrinkX, LinkBar» или «Сайт DAO — Нужен совет». В начале комментария — направления, модель, исходный блок сайта и полный вопрос клиента; далее контакты и номер. Стандартное поле `sourceDescription` дополнительно содержит блок и форму. Стандартные внешние поля `originatorId=DAO_COFFEE_WEBSITE`, `originId=requestId` связывают CRM с журналом.
6. Общая воронка `0`, стадия `NEW`, источник `STORE` («Веб-сайт»), ответственный из приватной серверной конфигурации. Существующий робот переводит в `UC_78BKC5` («Новая заявка»). Продуктовые заявки маршрутизируются одинаково.
7. Успех формы только после подтвержденного ID сделки. Созданный контакт без сделки успехом не считается.

## Текущее локальное хранилище (до PostgreSQL)

Ранее для одного Node.js API был реализован журнал SQLite: отдельного сервера БД и npm runtime-зависимостей не требуется. При нескольких независимых хостах нужна общая транзакционная БД; SQLite-файл не размещать на сетевой файловой системе.

| Таблица | Содержимое и назначение |
| --- | --- |
| `submissions` | `request_id` (серверный UUID), уникальный `idempotency_key` (UUID браузера), хеш нормализованного тела, `payload_json` со схемой v1, состояние, timestamps, время допустимого повтора, CRM entity/id и contact_id |
| `delivery_attempts` | Операция `send` или `reconcile`, время начала/окончания и безопасный результат. История не содержит URL вебхука, ответов CRM или IP |
| `delivery_lock` | Единственная lease-блокировка записи; атомарный захват и перепроверка состояния в `BEGIN IMMEDIATE`. Последовательная обработка нескольких процессов с одной локальной БД |

Снимок `payload_json`: `schemaVersion`, `name`, `phone`, `product`, `interests`, `model`, `comment`, `consent`, `source`. Он отражает запрос клиента, а не каталог товаров/цен. Время приема хранится сервером, согласие — ровно переданное формой значение; документ и версия юридического согласия не выдумываются. Каталожные `productId`, SKU, цена и количество отсутствуют в текущем UX, поэтому не создаются фиктивные товарные строки CRM.

Связь: одна заявка → много попыток → максимум один подтвержденный CRM ID у приложения. `originId` в Битриксе не уникальный индекс, поэтому именно локальный ключ и блокировки предотвращают повторные записи этого приложения. Внешние интеграции и ручные действия менеджеров не контролируются.

## Состояния и восстановление

- `received` — заявка сохранена, отправка ещё не началась. Например, другая заявка занимает lock. Ответ `503 DELIVERY_PENDING`; повторное ручное обращение с тем же ключом продолжает отправку.
- `processing` — попытка записана до сетевого вызова. После падения процесса неизвестно, дошёл ли запрос: по истечении lease (60 с) разрешена только проверка результата.
- `delivered` — ID сделки подтверждён и сохранён. Повтор возвращает прежний `requestId` без вызова создания.
- `rejected` — известный отказ; после backoff допустим ручной повтор с тем же ID. Контакт снова ищется перед созданием сделки.
- `unconfigured` — доставка не настроена; после исправления допустим ручной повтор.
- `uncertain` — результат неизвестен. Только чтение `crm.item.list` по двум внешним полям. Ровно одна карточка подтверждает доставку; ноль/несколько/ошибка остаются uncertain. Слепой новый `add` запрещен.

Отдельного фонового отправителя нет. Журнал позволяет видеть и разбирать недоставленные заявки, но сохранение не означает, что они будут отправлены без повторного запроса или оператора. Пока не согласован механизм ручного разбора, не выдавать pending за принятый менеджером заказ. Полная гарантия exactly-once между собственной БД и чужим REST недостижима; здесь выбран запрет повторной записи при неизвестном исходе.

## Хранение и эксплуатация

- Локально `LEADS_DB_PATH=backend/data/leads.sqlite`, на VPS `/var/lib/dao-coffee/leads.sqlite`. Каталог приватный, файл 0600, Git игнорирует БД/sidecars и `.env`. БД вне `site/`.
- База содержит персональные данные заявок. Ограничить доступ владельцем API, резервные копии хранить с теми же ограничениями. WAL нельзя резервировать простым копированием одного файла во время работы.
- Автоматического удаления нет, чтобы не стереть неопределённые операции и защиту от дублей. До production определить срок хранения и процесс удаления данных с сохранением минимальных ключей повторов. Нельзя очищать всю БД при каждом релизе.
- На фронте sessionStorage хранит только UUID и хеши контекста/содержимого; поля заявки не сохраняются. Закрытие вкладки/очистка storage теряет клиентский ключ: дедупликация между разными устройствами не обещается.
- Все серверные настройки назначения берутся из окружения. Посетитель не может выбрать портал, ответственного или поля CRM.

## Проверка

`npm run check` и `npm test` проверяют форму, API, запись SQLite, перезапуск, конкурентные запросы, потерянный ответ CRM, сверку по внешнему ID, повторную отправку и конфликты ключа. `npm run dev:backend` — исключительно локальный mock. `npm run inspect:bitrix` читает реальные метаданные без создания клиентов. Реальное создание записи и размещение сайта не выполнялись.

Источники: [универсальный create](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-add.html), [поля CRM](https://apidocs.bitrix24.ru/api-reference/crm/universal/object-fields.html), [поиск CRM](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html), [поиск контактов](https://apidocs.bitrix24.ru/api-reference/crm/duplicates/crm-duplicate-find-by-comm.html), [Node SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html).

Для оператора: `npm run journal:leads` показывает до 1100 номеров/состояний/CRM ID, сначала все незавершённые (их лимит — 1000) без персональных данных. `npm run journal:leads -- --reconcile <request-id>` проверяет только `processing/uncertain` через чтение CRM и обновляет локальный результат; новые карточки этот инструмент создавать не умеет. При 1000 незавершённых заявок новые заявки получают 503 до сохранения, существующие ключи продолжают проверяться. Нужны регулярный контроль журнала и разбор причин до достижения лимита.

## Как различается контекст обращения

`sourceId=STORE` — общий канал «Веб-сайт». Для текущей одной страницы конкретный блок однозначно выводится сервером из проверенных `source` + `product` без дополнительных полей браузера:

| Форма | Блок | Название / вопрос |
| --- | --- | --- |
| CTA DrinkX | `drinkx` | «Сайт DAO — DrinkX» + полный текст клиента |
| CTA LinkBar | `linkbar` | «Сайт DAO — LinkBar» + полный текст клиента |
| Другие CTA | соответствующий product ID | Wendougee / Кофе и СТМ / XLVI / Ceado / Водоподготовка / Комплектация |
| Hero с DrinkX + LinkBar | `hero` | «Сайт DAO — DrinkX, LinkBar» |
| Нижняя форма с выбором | `contact` | Выбранные направления, исходный блок остаётся нижним |
| Общая форма «Нужен совет» | `hero` или `contact` | «Сайт DAO — Нужен совет» |

Отдельной формы «технические данные» сейчас нет. Технический вопрос сохраняется в `comment`/«Вопрос клиента», классификация не угадывается по словам. На информационные карточки с моделью нельзя оставить отдельную заявку: текущие CTA передают `model=null`; если в будущем CTA явно получит `data-model`, модель появится в названии и комментарии. Сведения не записываются фиктивными товарными позициями и не создают отдельные воронки. При появлении второй CTA одного направления в другом блоке контракт нужно расширить проверяемым `sourceBlock`; текущий вывод предназначен для существующего HTML.
