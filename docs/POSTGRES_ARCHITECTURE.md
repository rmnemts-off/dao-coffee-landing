# PostgreSQL: единая БД сайта DAO

Реализация: `backend/postgres-store.mjs`, схема v1 — `backend/db/postgres-schema.sql`.
Production запускается с `DATABASE_URL`. Операции хранилища асинхронные через `pg`.
SQLite остаётся адаптером локального mock и источником одноразового импорта;
при недоступном PostgreSQL приложение не переключается на SQLite.

## Данные

В одной базе схема `dao_website`:

| Таблица | Что хранит |
| --- | --- |
| `customers` | Группировку обращений по нормализованному телефону, время первого/последнего обращения и однозначную связь с контактом CRM |
| `inquiries` | UUID заявки, ключ повтора, исходный хеш v1, снимок формы, имя/телефон, блок, направление, явно выбранную модель, комментарий, согласие и время |
| `directions`, `inquiry_directions` | Семь направлений сайта и многовыбор общей формы |
| `crm_deliveries` | Состояние, подтверждённые CRM ID, снимок назначения без секрета, lease-токен и поколение обработки |
| `delivery_attempts` | Историю отправок и проверок результата, без сырых ответов CRM и URL вебхука |
| `dispatch_lock` | Единую межпроцессную блокировку отправки |
| `upstream_cooldown` | Общую паузу после отказа CRM, сохраняющуюся после рестарта |
| `schema_migrations` | Версию схемы, проверяемую readiness |

Один телефон не доказывает личность человека: это группировка обращений, не
авторизованная учётная запись. Имя и комментарий каждой заявки сохраняются
отдельно. Разные CRM-контакты на одном телефоне помечаются как неоднозначность;
контакты Bitrix автоматически не объединяются и не редактируются.

Каждое новое обращение имеет самостоятельный UUID и сделку. Повтор HTTP-запроса
с прежним ключом не является новым обращением. Сайт не предоставляет публичного
API чтения истории по телефону. Каталога SKU, цен и товарных строк CRM нет;
направление DrinkX не подменяется выдуманным выбором S100/S400.

## Доставка

HTTP-контракт v1, маска телефона, контексты и черновики остаются прежними.
`reserve` в короткой транзакции блокирует строку dispatch_lock, проверяет прежний
ключ и лимит незавершённых заявок, создаёт клиента, снимок, направления и доставку.
Хеш старых записей переносится дословно: порядок ключей JSONB не используется
для его пересчёта. Неподдерживаемые JSONB строки (NUL/непарные surrogate) дают 400.

`claim` перепроверяет состояние, cooldown и lease в следующей короткой транзакции.
Попытка фиксируется до HTTP-вызова Bitrix; SQL-транзакция не удерживается во время
сети. `finish` проверяет токен, поколение и срок lease, записывает результат и
освобождает общую блокировку. Задержавшийся старый процесс не перезаписывает
результат нового. SQL-триггер дополнительно защищает подтверждения и запрещает
повторную отправку неопределённого результата.

`received/rejected/unconfigured` допускают явный повтор после паузы.
`processing/uncertain` допускают только чтение CRM по прежнему внешнему UUID.
`delivered` возвращает прежний успех без создания второй карточки. Ошибка
фиксации после ответа CRM оставляет результат неопределённым. Exactly-once между
PostgreSQL и сторонним REST не обещается. Фоновая отправка не добавлена.

Новые заявки сохраняют route (хост портала, тип сущности, категория, стадия,
источник, ответственный) без webhook-секрета. Если конфигурация изменилась,
незавершённая заявка блокируется до проверки оператора, а не уходит в новую CRM.
У импортированных исторических заявок неизвестный route остаётся NULL;
подтверждённые результаты при этом можно повторно получить без REST.

## Эксплуатация и перенос

Readiness проверяет подключение и версию схемы. Ошибки БД дают 503, ошибки после
CRM-записи — неопределённый исход без слепого повтора. При shutdown пул закрывается
после завершения фактических обработчиков, включая отключившихся клиентов.

На VPS PostgreSQL слушает только Unix-сокет; runtime-роль не владеет схемой и не
может удалять таблицы/заявки. Миграции выполняются отдельно. Секреты находятся вне
Git и публичного каталога. Импорт сохраняет прежние UUID, ключи, хеши, timestamps,
CRM ID и все попытки, проверяет их перед COMMIT. `processing` становится
`uncertain`, старые lease не переносятся. Некорректные данные останавливают импорт.

Порядок остановки приёма, резервирования, переключения и ограничения отката:
[deploy/POSTGRES.md](../backend/deploy/POSTGRES.md). После появления новых записей
в PostgreSQL нельзя запускать старый SQLite как актуальную базу.

Проверки на настоящем PostgreSQL: конкурентные процессы, лимит и связи,
lease takeover, поздний отказ и cooldown, потерянная фиксация после CRM,
импорт и повтор после перезапуска, HTTP-readiness при сбое БД, смена route.
Все CRM-вызовы в этих тестах имитируются; миграция не создаёт карточек в Bitrix.
