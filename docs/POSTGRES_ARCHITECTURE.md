# PostgreSQL: проект единой БД сайта DAO

Статус: **проект, не подключённый к runtime**. [SQL-прототип](../backend/db/postgres-schema.sql) предназначен для отдельной пустой тестовой PostgreSQL. Он не запускался на сервере или в CRM. В локальной ветке API остаётся существующий SQLite-журнал; текущий runtime на сервере этим проектом не изменяется. Документ не означает миграцию, установку PostgreSQL или публикацию сайта.

Проверенный серверный checkout — `8d7e28c`, без `store.mjs` и нового журнала. Установка и переключение действующего API остаются отдельным этапом.

## Что подтверждено кодом

`backend/store.mjs` сохраняет заявки, результаты CRM и попытки, но отдельной сущности клиента нет. `backend/delivery.mjs` повторяет подтверждённый результат и разрешает только чтение для `processing/uncertain`. `backend/bitrix.mjs` находит контакт по телефону и создаёт отдельную сделку. Эти гарантии нужно сохранить при смене хранилища.

В форме v1 `product` означает **направление/блок**: DrinkX, Wendougee, LinkBar, кофе, XLVI/Ceado, водоподготовка или комплектация. Это не каталожный ID оборудования. Общие формы передают несколько `interests` либо `undecided`. Все текущие брендовые CTA имеют пустой `data-model`; карточки моделей информационные. Поэтому «заявка на DrinkX» пока не означает выбор S100, S400 или AEROMILK.

Публичный контракт можно сохранить: `POST /api/leads`, тело v1 и UUID в `Idempotency-Key`. Ни новый клиентский идентификатор, ни технический выбор CRM в пользовательском сценарии не нужны. Деления на прайс и техническую консультацию нет.

## Одна БД, связанные таблицы

В одной PostgreSQL используется схема `dao_website`:

| Таблица | Назначение |
| --- | --- |
| `customers` | Внутренний UUID, уникальный нормализованный телефон `+7` и 10 цифр, первое/последнее обращение, необязательное однозначное соответствие контакту CRM |
| `inquiries` | Отдельная заявка: прежний `request_id`, уникальный `idempotency_key`, прежний хеш, снимок v1, имя/телефон на момент обращения, блок, модель, комментарий, согласие и время приёма. Адаптер не изменяет снимок после вставки |
| `directions` | Семь подтверждённых направлений из `validation.mjs`; в SQL есть их начальные значения |
| `inquiry_directions` | Направления конкретной заявки, включая многовыбор общей формы |
| `crm_deliveries` | Одна доставка на заявку, состояние, подтверждённые CRM ID, снимок назначения без секрета, токен/поколение обработки |
| `delivery_attempts` | История отправок и проверок результата без телефонов, URL вебхука и сырых ответов CRM |
| `dispatch_lock` | Общая lease-блокировка, сохраняющая последовательную запись первого варианта реализации |
| `schema_migrations` | Версия схемы; изменения выполняются отдельными миграциями |

Один клиентский профиль может иметь много заявок; каждая новая заявка имеет самостоятельный `request_id` и отдельную сделку. Повтор HTTP-запроса с прежним ключом не является новой заявкой. Существующая активная сделка не переиспользуется для нового обращения.

## Клиент и повторное обращение

В текущем UX единственный идентификатор связи — телефон. Нормализованный телефон позволяет группировать историю, но **не доказывает личность человека**: номер бывает общим для компании или меняет владельца. `customers` здесь — рабочая группировка обращений по номеру, а не учётная запись с подтверждённой личностью.

Имя каждой заявки сохраняется отдельно; новое имя не переписывает историю и не обновляет существующий контакт Bitrix. Разные имена на одном номере видны в снимках. При неоднозначном поиске CRM или нескольких исторических `contact_id` на одном номере `crm_match_state=ambiguous`, связь клиента с CRM не выбирается произвольно. Индивидуальные подтверждённые `contact_id` в доставках при этом сохраняются.

Составной внешний ключ `(customer_id, submitted_phone)` не позволяет привязать снимок одного номера к группировке другого. Телефон существующей группировки не изменяется при новом обращении с другого номера.

В первой реализации можно оставить поиск CRM по телефону для каждого нового обращения. Кэш `customers.crm_contact_id` заполняется только при однозначном результате, а не служит причиной без проверки привязать заявку к старой или объединённой карточке. Существующие контакты автоматически не сливаются. Профиль клиента не позволяет браузеру запрашивать историю других обращений по одному номеру.

## Контекст сайта и отображение в одной воронке

Сервер выводит контекст из проверенного v1, а не принимает произвольные поля CRM:

| Данные формы | Сохранение |
| --- | --- |
| `source=hero-modal` | `source_block=hero` |
| `source=inline` | `source_block=contact` |
| `source=brand-modal`, `product=drinkx` | `source_block=drinkx`, `product_code=drinkx`, одна строка направления |
| Общая форма с несколькими `interests` | Одна заявка и несколько строк `inquiry_directions` |
| `interests=["undecided"]` | Ноль строк направлений; выбор остаётся в исходном снимке |
| Явно выбранный `model` | `model_snapshot`; если выбора нет — `NULL` |

В SQL `source_block` вычисляется из `source/product_code`. Поле `issue_type` не вводится. При резервировании сервер атомарно записывает снимок и строки направлений; продуктовая заявка получает ровно своё направление, общая — проверенный набор. SQL обеспечивает FK/уникальность; соответствие массива v1 строкам связи дополнительно проверяется адаптером и тестами.

Для всех направлений сохраняется одна воронка Bitrix: категория `0`, начальная стадия `NEW`, источник `STORE` («Веб-сайт»), ответственный из проверенной серверной конфигурации. Существующий робот переводит сайт в `UC_78BKC5` («Новая заявка»). PostgreSQL не требует изменения роботов, стадий или CRM-режима.

Название сделки должно показывать выбранное направление и явно выбранную модель, если она есть. Комментарий содержит номер заявки, блок сайта, направления, модель, имя/телефон и сообщение. Повторность определяется наличием предыдущих **отдельных заявок** того же клиентского профиля, а не числом HTTP-попыток. Подтверждённые номера сделок предыдущих заявок позволяют менеджеру открыть историю. Вся эта информация готовится сервером, без нового вопроса посетителю.

Отдельный каталог товаров и товарные строки Bitrix сейчас не требуются: в UX нет SKU, цены и количества. Если позже появится явный выбор оборудования, добавить справочник моделей и проверенную связь модели с направлением. Не присваивать модели по наведению и не подменять отсутствие цены нулём.

## Приём и защита от повторов

1. Валидировать v1 и UUID ключа. Сформировать тот же нормализованный объект и алгоритм хеша версии 1, что и сейчас.
2. В короткой транзакции найти прежний ключ. Одинаковый ключ с другим хешем — `409`; прежний подтверждённый результат — ответ без создания CRM.
3. Для нового ключа атомарно получить/создать клиента по телефону, вставить заявку, её направления и `crm_deliveries=received`. Проверить лимит незавершённых записей в той же транзакции. Уникальные индексы, а не предварительный `SELECT` без блокировки, разрешают конкурентные вставки.
4. В следующей короткой транзакции захватить `dispatch_lock` и строку доставки, перепроверить состояние/срок повтора. Записать попытку, токен, поколение и `processing`, затем **COMMIT до HTTP-вызова**.
5. Выполнить прежний адаптер Bitrix. Транзакцию и блокировку SQL-соединения не держать открытыми во время сети. Сохранённая lease остаётся в БД.
6. Завершить попытку отдельной транзакцией только при совпадающих токене и поколении. `delivered` требует положительный CRM ID и допустимый тип сущности. Если CRM ответила успешно, а COMMIT потерялся, перечитать БД/CRM; не выполнять новый `add`.

Для неизвестного результата разрешён только `crm.item.list` с точными `originatorId=DAO_COFFEE_WEBSITE` и `originId=request_id`. Одно совпадение подтверждает доставку. Ноль, несколько, timeout или отказ чтения оставляют `uncertain`. Утрата lease не даёт новому исполнителю права повторить `add` для `processing`.

SQL-прототип дополнительно запрещает переход `uncertain` к новой отправке, возврат `processing` в `received`, превращение неудачной проверки результата в повторяемую отправку и изменение подтверждённой доставки. Сам по себе trigger не выполняет REST и не заменяет атомарную логику claim/finish в приложении.

Переход `processing/reconcile → processing/send` запрещён также с прежним токеном: промежуточная проверка не даёт обойти запрет новой записи. Продление действующей lease с той же операцией и токеном допустимо.

У Bitrix `originId` не является уникальным ключом. Транзакция PostgreSQL не включает чужой REST; обещать exactly-once нельзя. Сохраняется текущая безопасная семантика: локальная запись подтверждается отдельно, а успех формы — только после подтверждения сделки. Фоновая очередь не возникает автоматически при переходе на PostgreSQL.

## Что понадобится изменить в коде

- Добавить PostgreSQL-адаптер хранилища с теми же операциями `reserve/claim/finish/get/list/close`; операции станут асинхронными. Использовать параметризованные запросы и одну выделенную клиентскую сессию на транзакцию. Runtime-драйвер `pg` — отдельная явная зависимость будущей реализации.
- Перевести вызовы хранилища в `delivery.mjs`, запуск/завершение сервера и CLI на `await`. После появления `await` между reserve/claim нельзя полагаться на одну JS Map: атомарная перепроверка в PostgreSQL обязательна.
- Для начала сохранить одну общую lease, а не одновременно менять БД и распараллеливать CRM. Лимит незавершённых записей и захват lease защищать строкой-блокировкой/транзакцией, иначе два процесса могут пройти одну проверку лимита.
- Хранить `target_route` без секрета при первом резервировании: `portalHost`, `entityTypeId`, `categoryId`, `stageId`, `sourceId`, `assignedById`. Продолжение заявки использует прежнее подтверждённое назначение, а не незаметно изменившийся env. URL вебхука в БД не сохраняется.
- Для новых записей использовать PostgreSQL как единственный источник состояния. SQLite остаётся только входом миграции/архивом, не запасным runtime-хранилищем и не вторым местом записи.
- `DATABASE_URL` хранить только в закрытом серверном окружении; приложение подключается отдельной ролью без прав superuser/создания схем. Миграции выполняются отдельно. Фактическую установку, доступ и резервное копирование PostgreSQL проверяют на этапе серверного переключения.
- Для `bigint` CRM/attempt ID определить преобразование драйвера явно: `pg` может вернуть строку. Не подавать строку в существующий `Number.isSafeInteger` без проверенной конвертации и не терять точность.
- Схема использует `jsonb`, который не принимает NUL и некорректные Unicode surrogate-последовательности. Добавить согласованную валидацию таких строк до записи, чтобы корректно вернуть ошибку формы вместо внутренней ошибки БД.

## Перенос текущего журнала без потери подтверждений

1. Сначала только инвентаризация: существует ли реальный журнал, сколько записей в каждом состоянии, есть ли дубли CRM ID, повреждённые снимки или конфликтные контакты. Не публиковать payload/номера телефонов в отчёте. Если данных нет, импортировать нечего.
2. На отдельной тестовой PostgreSQL применить прототип и проверить импорт на обезличенных данных. Скрипт сам не создаёт БД, пользователей или сетевой доступ. Указание `DATABASE_URL` в инструкции не является разрешением запускать её на production.
3. Перед реальным переносом остановить приём новых заявок, дождаться завершения обработчиков и сделать согласованную резервную копию SQLite с учётом WAL. Не читать только основной файл живой WAL-базы. Проверить, что старый процесс больше не отправляет в CRM.
4. Импортировать в одной транзакции. Сохранить **без замены** `request_id`, `idempotency_key`, `payload_hash`, timestamps, `retry_at`, CRM entity/ID/contact ID и все попытки. Времена epoch milliseconds преобразовать без потери единиц. Идентификаторы попыток можно перенести явно; после этого поднять PostgreSQL identity sequence до максимума.
5. Создать группировки клиентов и направления из сохранённого проверенного снимка. Имена/сообщения/выбор модели не изменять. При одном телефоне и нескольких подтверждённых CRM-контактах не выбирать «первый»: сохранить контакты на доставках, клиента отметить неоднозначным.
6. Валидные `delivered` оставить подтверждёнными. `uncertain` оставить неопределёнными. Старые `processing` перевести в `uncertain` с сохранением незавершённой попытки; прежнюю lease не переносить. `received`, `rejected`, `unconfigured` сохранить. Некорректный `delivered` без положительного ID — `uncertain`, без догадок и повторного создания.
7. Старый SQLite не содержит полного снимка назначения. Не заполнять неизвестные исторические route-поля текущими значениями как установленным фактом: оставить `target_route=NULL` до проверки конфигурации той попытки. Это не мешает хранить уже подтверждённые CRM ID. Неопределённая доставка с неизвестным типом назначения требует отдельной проверки, не автоматического send.
8. **Не пересчитывать старый хеш через JSON.stringify прочитанного JSONB:** JSONB меняет порядок ключей. Перенести прежний хеш и его версию дословно; новые повторы сравнивать с тем же нормализованным алгоритмом v1. `originatorId` и `originId` в CRM не менять, существующие карточки не пересоздавать.
9. Сверить количество заявок/попыток, состояния, хеши и CRM ID. Дубликаты подтверждённого `(entity_type_id, crm_id)` остановят импорт из-за unique index: разобрать расхождение, не удалять данные ради прохождения ограничения.
10. Только после сверки переключить конфигурацию приложения на одну PostgreSQL. SQLite сохранить закрытым архивом. Не запускать оба runtime одновременно. Откат после новых PostgreSQL-записей требует переноса этих записей обратно или исправления вперёд; запуск старого снимка SQLite потеряет защиту от повторов.

## Проверки перед переключением

SQL smoke выполнен локально в PGlite 0.5.11 (PostgreSQL 18.6/WASM), без серверной БД и обращений в CRM: применение схемы, один клиент с двумя заявками, многовыбор, уникальность телефона/ключа/CRM-сделки, FK направления, обязательные ID подтверждения и ограничения переходов. Это проверка DDL и запросов; она **не заменяет многопроцессные тесты настоящего PostgreSQL, драйвера, блокировок и рестартов** будущего runtime.

- Две отдельные заявки одного телефона: один клиентский профиль, два снимка, две разные сделки; повтор одного ключа создаёт только одну.
- Одновременные запросы из двух процессов: одинаковый ключ не создаёт вторую запись; другой payload даёт 409; разные ключи одного телефона не создают два профиля.
- Сохраняются общая форма, многовыбор, `undecided`, блок и явно выбранная модель; отсутствие модели остаётся `NULL`.
- Потерянный ответ Bitrix, потерянный COMMIT, рестарт после `processing`, истёкшая lease, задержавшийся прежний исполнитель: неизвестный исход разрешает только чтение.
- После импорта подтверждённый ключ возвращает прежний `requestId` без REST create; неопределённый ключ также не отправляется заново.
- Восстановление backup, недоступная БД и повреждённые/неполные подтверждения не дают ложный успех. Readiness проверяет подключение и версию схемы, не создаёт тестовую карточку.
