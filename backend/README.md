# Заявки → Bitrix24

По решению владельца от 25.10.2026 заявки отправляются **только в Bitrix24**. Отправка, уведомления и резервная доставка в Telegram удалены. Рабочая ветка сохраняет прежнее имя `backend/telegram`.

`POST /api/leads` сохраняет JSON-схему версии 1 и состояния форм из [контракта](../docs/FORM_CONTRACT.md). Успех означает подтверждённое создание лида или сделки в CRM. Визуал, HTML, CSS и `main.js` не меняются. Сервер — Node.js со встроенными `http`, `fetch`, `crypto`, без runtime npm-зависимостей; `jsdom` нужен только DOM-тестам.

Проверки с mock выполнены. Доступ к реальному порталу и метаданные полей/источников/воронки проверены только чтением; контрольные CRM-записи не создавались. Nginx, Certbot, systemd и Grafana подготовлены в [deploy/](deploy/README.md), но наличие конфигурации в Git не означает её установку на VPS.

## Проверка локально

```sh
npm ci
npm run check
npm test
npm run dev:backend
```

Открыть `http://127.0.0.1:4322/`. Preview отдаёт только `site/` и API на одном origin. По умолчанию используется mock с задержкой 750 мс, **внешних запросов нет**, даже при заполненном `.env`. Успех здесь означает только успешный mock-ответ.

Другие исходы: `MOCK_DELIVERY_RESULT=rejected npm run dev:backend`; также доступны `uncertain` и `unconfigured`. `npm run dev` запускает только статику на 4321, без API. Preview запрещён при `NODE_ENV=production`.

## Подключение портала

1. В Bitrix24 создать входящий вебхук с правом `crm` под постоянным аккаунтом компании с правами чтения/создания нужных CRM-сущностей. Проверить доступность REST и подписки для конкретного портала. Вебхук даёт права владельца в пределах выбранного scope; это не доступ к личному кабинету через логин/пароль.
2. Добавить `BITRIX_WEBHOOK_URL` в локальный `.env` вне `site/`, `chmod 600 .env`. Если файл уже есть, дописать переменную, не перезаписывая существующие значения. В Git находится только пустой `.env.example`. URL с секретом нельзя помещать в браузерный код, PR, команды shell или логи.
3. Запустить `npm run inspect:bitrix`. Команда только читает режим CRM, описание полей, стадии и воронки; не читает карточки клиентов, не создаёт заявки и не меняет настройки. Выводит ограниченные метаданные, без URL вебхука. Для простой CRM возвращает стадии основной воронки; стадии выбранной дополнительной воронки нужно получить отдельно через `crm.status.list` с `ENTITY_ID=DEAL_STAGE_<categoryId>`.
4. Согласовать тип карточки, существующую воронку/стадию, одного ответственного и проверить доступ второго сотрудника в CRM. Заполнить оставшиеся переменные. Не подставлять примерные ID и не менять режим CRM ради интеграции.
5. Проверить обязательные поля, в том числе поля, обязательные на выбранной стадии. Если нужны дополнительные пользовательские поля, добавить согласованное сопоставление в адаптер после проверки портала. Сейчас произвольный набор полей из окружения или браузера не принимается.
6. Перед первой реальной записью согласовать тестовую карточку и проверить роботов на целевой стадии: создание через REST может запустить автоматизацию. Синтетическая заявка в Bitrix не считается разрешённой только потому, что раньше разрешались сообщения в тестовый Telegram-чат.

| Переменная | Назначение |
| --- | --- |
| `BITRIX_WEBHOOK_URL` | Полный HTTPS URL, заканчивается на `/rest/<user-id>/<secret>/`, без имени метода, query и fragment. Облачный или согласованный собственный домен, стандартный HTTPS-порт |
| `BITRIX_ENTITY_TYPE_ID` | Явно `1` — лид, `2` — сделка. Смарт-процессы не добавлены |
| `BITRIX_ASSIGNED_BY_ID` | Положительный ID согласованного ответственного, одинакового для всех форм |
| `BITRIX_STAGE_ID` | Реальный код начального статуса лида / стадии сделки; универсальный метод принимает `stageId` для обоих типов |
| `BITRIX_CATEGORY_ID` | Для сделок обязательно: реальный ID воронки; `0` допустим. Для лидов не используется |
| `BITRIX_SOURCE_ID` | Обязательно: существующий код источника CRM. На проверенном портале «Веб-сайт» = `STORE`. Источник формы отдельно сохраняется в комментарии |
| `LEADS_DB_PATH` | Путь к SQLite вне `site/`, обязательный для реальной CRM; локально `backend/data/leads.sqlite`, на VPS `/var/lib/dao-coffee/leads.sqlite` |
| `APP_ORIGIN` | Точный публичный HTTPS-origin сайта; без пути, query и credentials |
| `HOST`, `PORT` | Для VPS `127.0.0.1`, `4322` |
| `NODE_ENV` | Для VPS `production` |
| `TRUST_LOOPBACK_PROXY` | `1` только за локальным Nginx, перезаписывающим `X-Real-IP` |

`npm run start:backend` запускает API. Без полной конфигурации Bitrix запрос не уходит наружу и не возвращает ложный успех. В production неполная конфигурация останавливает запуск. Старые `TELEGRAM_*` переменные игнорируются, перехода к прежнему боту нет.

После согласования реальной проверки доступен `npm run dev:bitrix` на `http://127.0.0.1:4324/` (либо `PORT`). Это **реальная запись в CRM**, только по явному флагу `--bitrix`; неполные настройки приводят к отказу запуска. Старой команды `dev:telegram` больше нет.

## Что создаётся

- В классическом режиме с лидами: один `crm.item.add`, `entityTypeId=1`. Имя и телефон идут в штатные поля `name` и `fm`, статус и ответственный берутся из серверной конфигурации.
- В режиме сделки: сначала `crm.duplicate.findbycomm` по телефону. Единственный найденный контакт используется без изменения его имени/полей. При отсутствии совпадений создаётся контакт через `crm.item.add` (`entityTypeId=3`), затем сделка (`entityTypeId=2`) с `contactIds`, выбранными воронкой/стадией и ответственным.
- Если одному телефону соответствуют несколько разных контактов, операция завершается ошибкой до создания сделки: произвольный контакт не выбирается. Дубликаты нужно разобрать в CRM. Это ограничение текущего простого сопоставления по телефону.
- Название содержит DAO и направление. В комментарии сохраняются номер заявки, имя/телефон, направления, модель, пользовательский комментарий, контекст формы и переданное согласие. HTML и BBCode пользователя экранируются. Пустые поля не заполняются выдуманными значениями. Логирование IP и текста заявки отсутствует.
- `originatorId=DAO_COFFEE_WEBSITE`, `originId=requestId` помогают искать операцию в CRM. Это **не ключ идемпотентности** и не гарантия отсутствия дублей.

Контакт и сделка — отдельные операции, не транзакция: если контакт создан, а сделка не сохранилась, контакт может остаться в CRM. Успех формы в таком случае не показывается. Повторная попытка снова ищет контакт. Общий SQLite lock последовательно выполняет операции этого приложения, чтобы разные заявки с одним телефоном не создавали контакты одновременно. Другие интеграции Битрикса этим lock не управляются; полной уникальности телефона CRM не гарантирует. Существующие карточки автоматически не перезаписываются и не объединяются.

## Доставка и сбои

JSON-тело ограничено 8192 байтами, чтение — 5 секундами. Все вызовы Bitrix одной заявки имеют общий deadline 8 секунд, включая чтение ответа и создание контакта. После истечения deadline следующая операция создания не начинается, даже если прежний ответ пришёл поздно. Клиент ждёт до 20 секунд и сохраняет контекст/черновик при ошибке.

Успех `200 {ok:true, requestId}` возвращается только при корректном положительном ID **лида/сделки** в ответе CRM. HTTP 200 с полем `error` успехом не считается. Сырые ошибки и URL вебхука клиенту не возвращаются. Сетевые сбои, некорректные ответы и неопределённые серверные ошибки дают `502 DELIVERY_UNCERTAIN`: карточка могла сохраниться. Известный явный отказ даёт `502 DELIVERY_FAILED`; временно блокируются новые попытки. Автоматических повторов нет ни в адаптере, ни в Nginx.

Лимиты: 5 входящих POST/IP/мин, 30 попыток доставки или проверки/процесс/мин. Подтверждённые повторы не расходуют бюджет REST. Отправка требует UUID в `Idempotency-Key`; ключ и результат сохраняются в SQLite и переживают перезапуск. Для одного ключа ответ успеха повторяется без записи; другое тело даёт 409. Общая модальная и нижняя формы разделяют ключ при одинаковом содержимом. Новая намеренная заявка получает новый ключ.

SQLite хранит снимок заявки до первого REST-вызова, историю попыток и внутренние CRM ID. Неопределённый результат не истекает через пять минут: повтор разрешает только `crm.item.list` по внешнему ID. Ни таймаут, ни пустой результат поиска не разрешают новый `add`. При занятом lock возвращается `DELIVERY_PENDING`, при этом заявка остаётся в состоянии `received`; следующая ручная отправка с тем же ключом продолжает обработку. Фонового worker нет; неотправленные/неопределённые заявки требуют повторной проверки или оператора. Подробнее: [схема БД и поток данных](../docs/CRM_DATA_FLOW.md). Старый сервис памяти используется только тестами без настройки БД, реальная CRM без SQLite не включается.

`/healthz` проверяет процесс, `/readyz` — локальную конфигурацию и отсутствие draining. Они не обращаются к Bitrix и не доказывают REST-доступ/доставку; Nginx не публикует их. CLI пишет только request ID, результат и длительность; время события добавляет journald. При остановке API ждёт обработчики, в том числе вызов CRM после отключения посетителя, до 20 секунд; systemd ждёт 30 секунд.

## Проверки и источники

Тесты используют только mock Bitrix: поля лида/контакта/сделки, явные/неопределённые ошибки, timeout, запрет поздних записей, экранирование, дедупликация и лимиты. HTTP- и DOM-тесты проверяют origin, размер тела, IP-прокси, shutdown, маску +7, выбор направлений, черновики и двойную отправку. Настоящий портал и серверная установка требуют отдельных проверок.

Используется универсальное API: [crm.item.add](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-add.html), [поиск контактов по телефону](https://apidocs.bitrix24.ru/api-reference/crm/duplicates/crm-duplicate-find-by-comm.html), [входящие вебхуки](https://apidocs.bitrix24.ru/local-integrations/local-webhooks.html). Условия REST уточняются по [подписке Bitrix24](https://helpdesk.bitrix24.ru/open/24577700/).

## Проверенные параметры портала

Для подключаемого портала проверены чтением API: простой режим CRM (`2`), сделки `entityTypeId=2`, общая воронка `categoryId=0`, входная стадия `NEW`, источник сайта `STORE`, ответственный за заявки на продукцию задан в приватном `.env`. Текущий робот переводит этот источник в `UC_78BKC5` («Новая заявка»). Настройки роботов не менялись. Вебхук сохранён с scope CRM от согласованного пользователя; владелец ключа и ответственный сделки различаются. Секрет существует только в локальном `.env`, не в Git.

Новые контакт и сделка получают `opened: 'N'`. Тип продажи не форсируется: значения справочника портала переименованы. Направление/модель сохраняются в комментарии и БД, каталог товарных позиций и суммы не меняются.
