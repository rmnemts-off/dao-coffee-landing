# Заявки → Telegram

Реализован `POST /api/leads` по [FORM_CONTRACT.md](../docs/FORM_CONTRACT.md), версия 1. Визуал, HTML, CSS и `main.js` не изменены. Сервер — Node.js 22.9+ со встроенными `http`, `fetch` и `crypto`, без runtime-зависимостей. Минимальная версия нужна для запуска с необязательным `.env` через `--env-file-if-exists`. `jsdom` нужен только тестам существующего HTML и `forms.js`.

Для VPS выбрана схема Nginx + Certbot + один Node.js-процесс под systemd. Конфигурация и порядок размещения находятся в [deploy/README.md](deploy/README.md). Наличие конфигурации в Git не означает, что она уже установлена на сервере. Базы заявок, очереди, Bitrix и webhook для входящих сообщений бота нет. Для исходящей отправки `sendMessage` webhook не требуется.

## Локальная проверка без Telegram

```sh
npm ci
npm run check
npm test
npm run dev:backend
```

Открыть `http://127.0.0.1:4322/`. Этот сервер отдаёт только `site/` и API на одном origin. Telegram заменён mock-адаптером с задержкой 750 мс: **сообщения никуда не отправляются**, даже если в окружении есть реальный токен. Сообщение об успехе в этом локальном просмотре означает ответ mock. Не использовать preview для реальных заявок.

Чтобы проверить другие исходы, остановить preview и запустить:

```sh
MOCK_TELEGRAM_RESULT=rejected npm run dev:backend
MOCK_TELEGRAM_RESULT=uncertain npm run dev:backend
MOCK_TELEGRAM_RESULT=unconfigured npm run dev:backend
```

`npm run dev` по-прежнему запускает **только статический** сервер на 4321, без API. Проверять отправку нужно через `dev:backend`. `NODE_ENV=production` запрещает запуск mock preview.

## Конфигурация реального API

Скопировать пустой `.env.example` в `.env` вне `site/`, ограничить доступ к файлу (`chmod 600 .env`). `.env` игнорируется Git. Значения для сервера передать через окружение или этот локальный файл; в браузере токена и chat ID нет. Не вставлять их в команды, PR, скриншоты, логи или публичные конфиги.

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Токен согласованного бота; без пробелов |
| `TELEGRAM_CHAT_ID` | Согласованный числовой ID личного/группового чата либо username канала, где боту разрешена публикация. Имя самого бота не является адресатом заявки |
| `APP_ORIGIN` | Точный публичный origin сайта, например `https://dao.example`; без пути |
| `HOST` | По умолчанию `127.0.0.1`; рекомендуется за reverse proxy |
| `PORT` | По умолчанию `4322` |
| `NODE_ENV` | Для рабочего размещения `production` |
| `TRUST_LOOPBACK_PROXY` | `1` только если API доступен лишь через локальный proxy, который **перезаписывает** `X-Real-IP`. По умолчанию заголовки прокси не используются |

```sh
npm run start:backend
```

API отдаёт `/healthz` для проверки процесса и `/readyz` для проверки локальной конфигурации и готовности принимать заявки. Проверки не обращаются в Telegram и не подтверждают доставку. В production Nginx не публикует эти адреса. Без токена или адресата POST получает `503`, успех не имитируется. В `production` отсутствие токена, адресата или origin останавливает запуск.

Реальную проверку проводить только после согласования **конкретного тестового чата**. Для личного чата пользователь должен начать переписку с ботом; для группы бота нужно добавить с правом отправки. Нельзя выбирать получателя по первому элементу `getUpdates` или публичным контактам сайта. 25.10.2026 реальная доставка синтетической заявки через локальный `POST /api/leads` проверена в согласованном личном чате: получены подтверждение API и видимое сообщение Telegram. Получатель установлен по уникальной команде, которую пользователь отправил боту; токен и адресат сохранены только в игнорируемом `.env` с правами `600`.

Бот используется как отправитель уведомлений с сайта. Постоянного polling/webhook и автоответа на `/start` в этом сервисе нет. Само сообщение `/start` не создаёт заявку: её создаёт форма сайта через API. Локальный mock preview по-прежнему не отправляет сообщения; для реальной доставки нужен запущенный API с серверными переменными окружения.

Для проверки **форм сайта с настоящей отправкой** после согласования получателя и заполнения `.env` запустить `npm run dev:telegram`, открыть `http://127.0.0.1:4324/` (либо порт из `PORT`). Сервер доступен только на loopback и отдаёт только `site/`; API находится на том же origin. Каждая новая корректная заявка уходит настроенному получателю. Этот запуск явно включает `--telegram`, без токена/адресата завершается с ошибкой; обычный `dev:backend` сохраняет mock-режим. Одновременно запускать API и preview на одном порту нельзя. Оба режима preview запрещены при `NODE_ENV=production`.

## Размещение на VPS

Готовятся Nginx, Certbot и systemd: [порядок установки, выпуска и отката](deploy/README.md), [конфигурация Nginx](deploy/nginx/README.md). Для production используется Node.js 24 LTS; API не требует установки npm-зависимостей. Сборки фронтенда нет.

Nginx отдаёт только `/srv/dao-coffee/current/site/`, а точный `/api/leads` проксирует на `127.0.0.1:4322`. Сайт и API находятся на одном HTTPS-origin. Nginx перезаписывает `X-Real-IP`, API получает `TRUST_LOOPBACK_PROXY=1`. Автоматических повторов POST нет. Перед добавлением CDN или контейнерной bridge-сети нужно пересмотреть доверие к прокси.

Секреты хранятся вне релизов и публичного каталога, в `/etc/dao-coffee/api.env`. Работает один непривилегированный процесс API: лимиты и дедупликация общие только внутри него. При SIGTERM прекращается приём новых заявок, завершение активной обработки ожидается до 20 секунд; systemd даёт процессу 30 секунд до принудительного завершения.

По отдельному поручению добавлена конфигурация мониторинга: [Grafana, Prometheus и node_exporter](deploy/monitoring/README.md). Все три интерфейса привязаны к loopback; Grafana открывается через SSH-туннель. Метрики сервера не содержат заявки. Мониторинг не является защитой от DDoS и сам по себе не доказывает доставку Telegram.

Перед публичным приёмом заявок остаются настройка сервера и домена, production-секреты, подтверждённый рабочий адресат и документы для обработки персональных данных. Ранее выполненная локальная отправка подтверждает только работу согласованного тестового чата. Публикация сайта и DNS выполняются отдельным действием после команды владельца.

## Доставка, повторы и ограничения

- Сервер независимо проверяет контракт, согласие, формат `+7`, направления и длины. Максимум JSON-тела — 8192 байта; чтение тела — 5 секунд. HTML пользователя экранируется перед форматированием Telegram.
- Успех `200 {ok:true, requestId}` возвращается только после `ok:true` и корректного `message_id` от Telegram. Идентификатор создаётся сервером и включается в сообщение.
- На один IP разрешено 5 входящих POST в минуту; невалидные и повторные попытки расходуют этот лимит. Отдельный лимит процесса — 30 новых отправок в Telegram за минуту. Невалидные заявки и ответы из дедупликации не расходуют бюджет отправок. Это базовая защита формы, не защита от DDoS. В памяти не более 10 000 IP-хешей и 1000 записей доставки; при заполнении обработка отклоняется без удаления активной защиты от дублей.
- Одинаковые нормализованные заявки объединяются при одновременной отправке; подтверждённый результат хранится 5 минут. Общая модальная и нижняя формы считаются одной заявкой при совпадении содержимого, независимо от `source`. Направление и явно выбранная модель входят в идентичность заявки. Повтор с тем же содержимым в этом окне возвращает прежний результат.
- В памяти остаются HMAC-хеши и результаты, а не журнал заявок. Незавершённая отправка держит данные только до завершения вызова. После перезапуска память очищается. **Гарантии exactly-once после перезапуска или истечения 5 минут нет.** Это осознанное ограничение без добавления БД/очереди и изменения контракта.
- Telegram timeout — 8 секунд, включая чтение ответа. При сетевом сбое, 5xx или некорректном ответе возвращается `502 DELIVERY_UNCERTAIN`: сообщение могло быть доставлено. Этот результат также подавляет идентичные повторы на 5 минут. Автоматических повторов нет. При явном 4xx-отказе Telegram — `502 DELIVERY_FAILED`; новые отправки приостанавливаются минимум на 5 секунд, при 429 учитывается `retry_after`.
- Клиент ждёт до 20 секунд и блокирует обе общие формы на время их общего запроса. Поля не очищаются; черновики остаются в памяти страницы. Можно закрыть модальное окно и открыть другое направление; завершение старого запроса не меняет чужой контекст и не перехватывает фокус.
- При непонятном результате форма не обещает доставку, предупреждает о возможной отправке и предлагает существующие контакты. Повторять вручную сразу нельзя: Telegram не поддерживает ключ идемпотентности для `sendMessage`.
- Рабочий API пишет только безопасные события доставки: время, случайный request ID, результат и длительность. Тела заявок, IP, токены, chat ID и upstream-ошибки в логи не попадают. Резервные копии секретов и политика хранения данных в самом Telegram настраиваются отдельно при сдаче.

## Проверки

`npm test` проверяет серверную валидацию, все направления, HTML-экранирование, положительный/отрицательный ответ Telegram, timeout HTTP и тела ответа, дедупликацию и лимиты. HTTP-тесты поднимают сервер только на loopback и проверяют размер потокового тела, Origin, content type и подделку прокси-заголовков. DOM-тесты исполняют текущий `forms.js` на реальном HTML проекта с mock fetch: маска, несколько направлений, consent, сохранение черновиков, закрытие и переиспользование dialog, двойное нажатие, неопределённый ответ.

Все данные тестов синтетические. Внешние сообщения не отправляются. Проверка в браузере и проверка с реальным Telegram — разные этапы; локальный mock не подтверждает права бота или правильность адресата.
