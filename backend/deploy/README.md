# VPS: Nginx, Node.js и мониторинг

Конфигурация для одного Linux VPS: Nginx отдаёт `site/` и проксирует `/api/leads` на единственный Node.js 24 LTS процесс под systemd. Certbot обслуживает HTTPS. Отдельно устанавливаются Grafana, Prometheus и node_exporter с доступом только через loopback и SSH-туннель.

Фактически установленная инфраструктура и результаты проверки после перезагрузки зафиксированы в [статусе VPS от 25.10.2026](STATUS.md). Nginx пока обслуживает holding-ответ, мониторинг работает отдельно; API и лендинг ещё не опубликованы. Ниже описана процедура размещения. Она предполагает поддерживаемый Debian/Ubuntu и требует проверки фактической ОС, имеющихся сервисов и домена. Публикация сайта, смена DNS и слияние PR выполняются по отдельной команде владельца.

## До установки

Через SSH проверить `/etc/os-release`, `uname -m`, `free -m`, `df -h`, `ss -lntp` и установленные сервисы. Не заменять существующие конфиги без чтения и резервной копии. Мониторинговый установщик рассчитан только на новую установку и откажется менять существующую.

Административный доступ и пользователь приложения разделены. Создать системного пользователя `dao-coffee` без интерактивного входа и sudo. Не отключать существующий SSH-доступ до проверки замены и аварийной консоли. API, Grafana и сборщики не публикуются отдельными внешними портами.

Проверить, что `/usr/bin/node` — актуальный исправленный выпуск ветки 24 LTS. Unit проверяет major 24. Node устанавливается из проверенного официального/подписанного источника для фактической ОС; не запускать произвольный загрузочный shell-скрипт от root. На VPS приложение не требует `npm install`: runtime-зависимостей нет.

## Файлы и секреты

```text
/srv/dao-coffee/releases/<commit>/   принятый релиз: site/ + backend/
/srv/dao-coffee/current             ссылка на текущий релиз
/etc/dao-coffee/api.env             секреты, root:root, 0600
/etc/systemd/system/dao-coffee-api.service
/etc/nginx/                        установленные конфиги, вне релиза
/etc/letsencrypt/                  сертификаты Certbot
```

Каталоги релиза принадлежат администратору и доступны API и Nginx только для чтения. Не размещать `.env`, `.git`, `node_modules` или рабочие файлы с доступами в `site/` либо в архиве релиза. `/etc/dao-coffee` — root:root, 0700; systemd читает `api.env` до понижения привилегий. Значения `NODE_ENV=production`, `HOST=127.0.0.1`, `PORT=4322`, `TRUST_LOOPBACK_PROXY=1` проверяются unit. `APP_ORIGIN` — точный согласованный HTTPS-origin. Вебхук и параметры CRM задаются по [API-инструкции](../README.md).

## Ручной выпуск

1. Принять PR в `main` отдельно от публикации. Выбрать конкретный SHA, проверить его в отдельном чистом checkout: `npm ci`, `npm run check`, `npm test`. Убедиться, что статические файлы и API принадлежат одному релизу. На сервере не собирать рабочую ветку с незавершёнными изменениями коллеги.
2. Создать архив **отслеживаемых** `site/` и `backend/` из принятого коммита через `git archive`, записать SHA и checksum. Проверить состав архива до загрузки. Секреты в архив не включаются.
3. Распаковать в новый `/srv/dao-coffee/releases/<SHA>/`, проверить код и права. Путь `current` никогда не указывает на каталог, куда ещё загружаются файлы.
4. Для первого запуска установить unit, secrets и Nginx по связанным инструкциям. `nginx -t` и `systemd-analyze verify /etc/systemd/system/dao-coffee-api.service` обязательны на целевом Linux. HTTP bootstrap открывает только ACME, остальному отвечает 503. Выпуск сертификата и включение HTTPS выполняются после согласования домена/DNS.
5. При обновлении остановить `dao-coffee-api.service` и дождаться завершения. Приложение ждёт активные операции до 20 секунд, systemd — 30. Переключить ссылку `current` на полностью готовый релиз атомарным переименованием временной ссылки и запустить API. В это короткое окно формы могут получить ошибку, их заполнение сохраняется. Автоматических повторов POST нет.
6. Проверить локальные `GET /healthz` и `GET /readyz`, состояние unit, HTTPS, загрузку сайта и закрытые служебные маршруты. Readiness не подтверждает Bitrix24. Реальную контрольную заявку отправлять только с синтетическими данными в согласованное место CRM.

Не запускать две версии API параллельно: у каждой отдельные лимиты и дедупликация. Хранить минимум два предыдущих проверенных релиза; не удалять релиз, на который указывает `current`.

## Откат и резервирование

При неуспешной проверке остановить API, вернуть `current` на предыдущий SHA, восстановить совместимую конфигурацию, запустить и проверить API. Перед reload Nginx всегда выполнять `nginx -t`. Изменение секретов и сертификатов не является обычным откатом кода.

Сохранять зашифрованную копию `/etc/dao-coffee`, конфигурации Nginx/systemd/мониторинга и `/etc/letsencrypt` вне VPS. Grafana SQLite копируется при остановленном сервисе; подробнее в инструкции мониторинга. Проверить восстановление, а не только наличие архива. Копия диска не сохраняет память API: после рестарта исчезают лимиты и пятиминутная дедупликация. Постоянной базы/очереди заявок здесь нет.

## Проверка после установки

- Службы активны и включены на загрузку; приложение работает непривилегированным пользователем.
- `ss -lntp`: 4322/3000/9090/9100 слушают только loopback; внешние firewall-правила их не открывают.
- Nginx отдаёт только `site/`, не публикует секреты/служебные маршруты и перезаписывает IP-заголовок.
- Готовность API проверяется без отправки сообщений. Логи не содержат заявки и секреты.
- `monitoring/validate.sh` проходит; в Grafana видны свежие значения, а не только импортированный пустой дашборд.
- Свободная память/диск проверены после запуска. Лимиты сервисов не заменяют измерения реального потребления.

Мониторинг показывает CPU, память, диск и сетевой трафик. Он не защищает канал VPS от DDoS, не определяет сам по себе причину роста трафика и не подтверждает доставку заявок. Настройка автоматических уведомлений требует согласованного канала; сейчас сообщения от мониторинга не отправляются.
