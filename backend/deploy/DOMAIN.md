# Перенос работающего IP-сайта на домен

Эта процедура сохраняет HTTPS и HTTP-01 для IP во время подготовки. После переключения IP и дополнительные имена перенаправляются на один канонический домен. CRM, её вебхук, воронка и ответственный не меняются. Никаких новых контрольных карточек процедура не создаёт.

`prepare-domain.py` только генерирует файлы. `domain-preflight.py` проверяет DNS и публикует один временный случайный ACME probe, который затем удаляется; по умолчанию сертификаты и службы не меняет. Явный `--issue` после успешной проверки запускает Certbot, но не переключает сайт. Скрипты требуют только Python 3. Готовые bundles хранить вне репозитория и `site/`.

## 1. Подготовить до изменения DNS

Подтвердить основной домен и список aliases. Пример использует зарезервированный `coffee.example`; заменить его на подтверждённое имя. `www` включается только явным `--alias`.

```sh
python3 backend/deploy/prepare-domain.py \
  --domain coffee.example --alias www.coffee.example \
  --ipv4 203.0.113.10 --output /root/dao-domain-bundle
```

Сначала проверить старый vhost и сохранить резервную копию вне публичных файлов. Для обновлённого общего `dao-private-locations.conf` убрать дубли запрета `/design-system` из старого IP-vhost; устанавливать совместимые версии обоих файлов вместе. После подготовки `nginx -t` обязателен. На занятом VPS не запускать установщики мониторинга заново.

Установить **bootstrap из bundle** вместо текущего `dao-coffee.conf`, проверить `nginx -t`, затем сделать reload. Bootstrap оставляет IP-сайт и его API работающими; доменные имена на HTTP получают `503`, кроме HTTP-01 challenge. Он не требует ещё не выпущенного доменного сертификата. **Не заменять IP-конфиг отдельным доменным шаблоном**: это отключит TLS и продление сертификата для IP.

До DNS проверить в частности:

```sh
curl --resolve coffee.example:80:203.0.113.10 -I http://coffee.example/
curl --resolve www.coffee.example:80:203.0.113.10 -I http://www.coffee.example/
```

Ожидается `503`, а по текущему HTTPS IP — прежний сайт с доверенным сертификатом. Для проверки ACME положить случайный файл только в `/var/lib/letsencrypt/.well-known/acme-challenge/`, проверить `200` и совпадение тела для каждого Host, затем удалить только этот файл. Секреты туда не копировать.

## 2. DNS

**Для уже действующего домена HTTP-01 означает окно недоступности доменного HTTPS между сменой DNS и выпуском/активацией сертификата.** IP-сайт в это время работает. Планировать переключение и выпуск вместе, а не менять DNS за часы до запуска оператора. Если окно недопустимо, сертификат нужно получить заранее, например через DNS-01; для этого требуется отдельный доступ к DNS и проверенный способ автоматического продления. Эта процедура DNS-01 не настраивает.

- A основного домена → IPv4 VPS; несколько старых A не оставлять.
- Для `www`: CNAME на основной домен **или** A на IPv4 VPS. Не создавать CNAME и A для одного имени одновременно.
- Удалить старую AAAA, если рабочий IPv6 VPS не настроен. Этот bundle и preflight рассчитаны на IPv4 без AAAA.
- Если есть CAA, убедиться, что она допускает `letsencrypt.org`; проверить также наследуемую CAA. Не стирать ограничения без согласования.
- MX, TXT/SPF/DKIM/DMARC и NS не менять: перенос сайта не требует переноса почты или DNS-провайдера.
- По возможности заранее снизить TTL записей сайта, учитывая прежний TTL. Проверить ответы авторитетных NS и нескольких публичных резолверов; один локальный ответ не доказывает распространение DNS.

После распространения DNS на VPS выполнить:

```sh
python3 backend/deploy/domain-preflight.py /root/dao-domain-bundle
```

Скрипт должен подтвердить **каждое** имя и HTTP-01 без перенаправления. При несовпадении DNS или `503`/`404` на challenge сертификат пока не запрашивать. Проверку challenge желательно повторить извне VPS.

## 3. Выпустить сертификат

На существующем VPS использовать **только** `/opt/dao-certbot/bin/certbot`. Старый `/usr/bin/certbot` не обслуживает текущую IP-конфигурацию. Используется уже зарегистрированный ACME account; email владельца не выдумывать.

```sh
/opt/dao-certbot/bin/certbot certonly --non-interactive \
  --webroot --webroot-path /var/lib/letsencrypt \
  --cert-name dao-domain -d coffee.example -d www.coffee.example
```

Список `-d` должен в точности покрывать `domain.json`; если `www` не согласован, его не включать. Нельзя включать HTTPS redirect для `www` до наличия `www` в SAN сертификата. При неудаче оставить bootstrap и рабочий IP; не повторять выпуск циклически.

Эквивалент с автоматической подстановкой имён из проверенного bundle и обязательным preflight: `python3 backend/deploy/domain-preflight.py /root/dao-domain-bundle --issue`. Он не делает reload и не меняет origin.

Сертификат хранится в `/etc/letsencrypt/live/dao-domain/`. Проверить SAN, срок, доверенную цепочку и доступность соответствующего private key для root, не печатая ключ. Короткоживущий `dao-ip` сохраняется: он нужен, чтобы HTTPS по IP мог безопасно перенаправлять на домен.

## 4. Переключить origin и vhost вместе

Сохранить root-only копии текущего vhost и `/etc/dao-coffee/api.env` в отдельном каталоге отката (`0700`, секретный файл `0600`). Остановить `dao-coffee-api`, дождавшись graceful shutdown. Изменить **только** `APP_ORIGIN` на точное `https://coffee.example` в env, не выводя остальное содержимое и не меняя Bitrix-переменные. Установить `dao-domain-https.conf` из того же bundle, выполнить `nginx -t`, запустить API и проверить loopback `/readyz`, затем reload Nginx. При ошибке до первого успешного reload восстановить оба прежних файла, запустить API и проверить прежний Nginx. Сохранить исходный успешный релиз для отката.

Переключение короткое, но не атомарно между процессами: в этом окне отправка может вернуть ошибку; форма сохраняет заполнение. Уже открытые вкладки по IP нужно обновить и перейти на домен — старый Origin намеренно не добавляется в разрешённые. POST не повторять автоматически.

Проверить без реальной заявки: HTTPS основного имени `200`, IP `307` без кеширования и aliases `308` на основной домен, GET `/api/leads` → `405`, невалидный JSON `{}` с правильным Origin → `400`. Проверить `/.env`, `/healthz`, `/metrics`, `/grafana/`, `/design-system/` → `404` на основном домене, закрытые порты и неизменность файлов релиза. Невалидный POST не обращается в CRM.

## 5. Автопродление и откат

Один существующий `dao-certbot-renew.timer` обслуживает оба lineage. Новые timers не нужны, старый `certbot.timer` остаётся выключенным.

```sh
/opt/dao-certbot/bin/certbot renew --cert-name dao-domain --dry-run --run-deploy-hooks
systemctl is-enabled dao-certbot-renew.timer
systemctl list-timers dao-certbot-renew.timer
```

После проверки домена убедиться, что HTTP-01 для IP тоже сохранился. Проверить deploy hook с ограничениями systemd, описанными в [Nginx README](nginx/README.md).

**Откат после успешной активации отличается от возврата bootstrap:** восстановить проверенный релиз и старый IP-origin в env, но установить `dao-domain-rollback.conf` из bundle. Этот fallback сохраняет оба сертификата: домен и aliases через HTTPS перенаправляют на IP, а IP снова отдаёт сайт и API. Проверить `nginx -t`, `/readyz`, запустить/reload службы и проверить оба HTTPS адреса. Обратимые переходы IP → домен и домен → IP используют `307` с `Cache-Control: no-store`: постоянный закешированный redirect мог бы вызвать цикл при откате. HTTP-01 остаётся доступным для обоих lineage. Возврат одного bootstrap после активации отключил бы доменный TLS, поэтому так не откатывать. DNS откатывается отдельно с учётом кешей; сертификаты не удалять.

Основания: [Certbot webroot и несколько имён](https://eff-certbot.readthedocs.io/en/stable/using.html#webroot), [Let’s Encrypt HTTP-01 и порт 80](https://letsencrypt.org/docs/challenge-types/#http-01-challenge), [проверка CAA](https://letsencrypt.org/docs/caa/).
